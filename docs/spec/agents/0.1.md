# Hooknostic Agent Definition 0.1

**Status:** provisional draft, 2026-09-29. Proposed by
[ADR-0027](../../decisions/0027-portable-agents.md), which is not yet accepted.
Hooknostic's build reads this format through `components.agents`, for project
and package delivery.

An agent definition describes one agent that a harness can run. The harness runs
it in one of two ways, or both:

- **As a subagent.** The agent a session runs as hands it a task, and it works
  in a child session. Claude Code calls these "subagents", Codex calls them
  "custom agents", and OpenCode calls them agents with `mode: subagent`.
- **As the agent a session runs as.** OpenCode calls these primary agents. Claude
  Code runs any subagent this way when a session is started as it. Codex has no
  such agents.

This document defines one portable file for that concept. Hooknostic translates
the file into each harness's native format.

## Why this is a Hooknostic format, and how it can be replaced

No cross-vendor standard defines agents. Agent Plugins 1.0 deliberately leaves
them out: "commands, hooks, agents, rules, and LSP servers — remain too
client-specific for a stable portable contract and are outside the v1 format until
their formats converge." Hooknostic already fills that gap for hooks, and this
format fills it for agents. It is designed so that a real standard can take its
place:

- **A small closed core.** The core is `name`, `description`, `mode` and the
  instructions, spelled the way the harnesses already spell them. It is the
  smallest shape that a later standard is likely to share.
- **Harness-specific data is quarantined.** It lives under `native`, keyed by
  harness. A converter can carry it forward or drop it without touching the core.
- **Consumers work from a model, not from this file.** A consumer parses the file
  into the model in [Model](#model), and translates only from the model. If a
  standard emerges, it becomes a second parser into the same model. The
  translators do not change, and 0.1 files can be converted mechanically.
- **Evidence decides what is portable.** A field joins the core only when captured
  evidence shows the harnesses can honour it, or that a consumer can report
  where one cannot (see [Fields held back](#fields-held-back-from-01)).

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as
described in RFC 2119.

## File

- **Encoding.** A definition is one UTF-8 Markdown file, and the file holds one
  definition.
- **Frontmatter.** The file MUST begin with a YAML frontmatter block. The block
  opens with a line `---` and closes with the next line `---`.
- **Mapping.** The frontmatter MUST be a YAML mapping. It MUST NOT use anchors,
  aliases or custom tags.
- **Instructions.** Everything after the closing `---` is the **instructions**.
- **Name.** The file is named `<name>.md`, where `<name>` is its `name` field.
- **Folders.** A consumer reads the definition files directly inside a configured
  source directory. A consumer MUST NOT treat subdirectories as part of a name.

## Frontmatter fields

The key set is closed. A key not listed here makes the file invalid. Future
versions can then add fields without colliding with content that already exists.

| Field | Required | Value |
| --- | --- | --- |
| `name` | yes | 1–64 characters: lowercase ASCII letters and digits in hyphen-separated runs (`^[a-z0-9]+(-[a-z0-9]+)*$`). It MUST equal the file stem. |
| `description` | yes | 1–1024 characters on a single line. It says **when** to use this agent. |
| `mode` | no | `subagent` (the default), `primary` or `all`; see [`mode`](#mode). |
| `native` | no | A mapping from a harness key to a mapping of that harness's own agent fields; see [`native`](#native). |

The instructions MUST contain at least one non-whitespace character.

`name` follows the Agent Skills name grammar. That grammar is the intersection of
what the targeted harnesses accept, so one name survives every translation.

`description` is the text a harness shows to route work: to the agent that
delegates, for a subagent, and in the harness's agent list. The single-line rule
keeps it intact through every harness's frontmatter or TOML encoding.

### `mode`

`mode` says where the agent is offered. The values are OpenCode's, the one
targeted harness that has such a field:

| Value | Offered for delegation | Offered as the agent a session runs as |
| --- | --- | --- |
| `subagent` (default) | yes | no |
| `primary` | no | yes |
| `all` | yes | yes |

A file without `mode` defines a subagent.

### `native`

`native` carries fields that only one harness understands:

```yaml
native:
  claude:
    model: sonnet
  codex:
    model_reasoning_effort: high
```

- **Keys.** A key is a consumer's harness identifier. Hooknostic's are `claude`,
  `codex` and `opencode`. A consumer MUST reject a key it does not know, so a
  misspelled harness fails instead of being dropped.
- **Values.** Each value is a mapping. The consumer emits it only into that
  harness's native file. A consumer MUST NOT copy one harness's native fields into
  another harness's output.
- **Validation.** Values are the harness's own vocabulary, so this document does
  not define them. A consumer SHOULD validate what it can, because a harness may
  punish an unknown field: Codex drops the whole agent file (`.capture/agents`).
- **Reserved keys.** A `native` mapping MUST NOT set a field that the portable core
  owns:

  | Harness | Refused native keys |
  | --- | --- |
  | `claude` | `name`, `description` |
  | `codex` | `name`, `description`, `developer_instructions` |
  | `opencode` | `name`, `description`, `prompt`, `system`, `mode` |

  A consumer MAY refuse further keys. For example, Hooknostic refuses keys that
  would embed another component kind it validates on its own, such as per-agent
  hooks or MCP servers.

## Model

A consumer parses a valid file into:

```ts
interface AgentDefinition {
  name: string;
  description: string;
  mode: "subagent" | "primary" | "all"; // "subagent" when absent
  instructions: string;
  native: Record<string, Record<string, unknown>>; // empty when absent
}
```

A future source format that maps onto this model can be consumed by the same
translators.

## Semantics

A consumer that delivers a definition to a harness MUST arrange the following.

For a definition whose mode is `subagent` or `all`:

1. **Availability.** The harness offers the agent to the agent a session runs as,
   through the harness's own delegation mechanism, under its `name`, or under a
   name qualified by its package when a package route requires one.
2. **Routing.** The harness shows the delegating agent the `description`.
3. **Instructions.** A child session started for the agent receives the
   instructions at system or developer level.

For a definition whose mode is `primary` or `all`:

4. **Selection.** The harness lets a user start a session as the agent, by its
   `name` or its package-qualified name, through the harness's own mechanism.
5. **Instructions.** A session running as the agent receives the instructions at
   system or developer level.

For a definition whose mode is `primary`:

6. **No delegation.** The harness does not offer the agent for delegation.

A harness may be unable to honour a mode. Codex has no agent a session can run
as, so it cannot deliver a `primary` definition, and delivers an `all` definition
as a subagent only. Claude Code offers every agent it knows for delegation. A
consumer MUST report each definition whose mode it cannot fully honour, and it
MUST NOT silently omit one. Hooknostic reports through its component support
levels and shortfall policy.

The following are **not** guaranteed by this version. Authors should write with
that in mind:

- **The base prompt may be replaced.** A harness MAY keep its own base prompt and
  add the instructions to it, or replace it. Claude Code and OpenCode replace it;
  Codex adds to it (`.capture/agents`). Instructions SHOULD be self-contained.
- **The model is harness-defined.** Without a `native` model the harness default
  applies, and those defaults differ. A native model may also apply to one use of
  an agent and not the other: OpenCode 2.0.17 runs a session started as the agent
  on its configured model.
- **The default agent.** A `mode` makes an agent available; it does not make it
  the agent a session starts as. A consumer MAY offer that as configuration
  outside this format, as Hooknostic's `components.defaultAgent` does.
- **Running a subagent as a session.** Claude Code and OpenCode 2.0.17 let a user
  start a session as any agent they know, a `subagent` included; OpenCode
  1.18.31 refuses.
- **Tools, permissions, sandboxing, turn limits, skills, MCP servers and hooks**
  keep each harness's default for the agent unless `native` sets them.

## Fields held back from 0.1

The following names are reserved. A 0.1 file MUST NOT use them as top-level keys,
because a later version may define them. The reasons are what the captures found
(`.capture/agents`).

| Reserved | Why it is not portable yet |
| --- | --- |
| `readOnly`, `tools` | A read-only posture maps to exact tool removal on Claude, to permission rules on OpenCode (v2 keeps `subagent` and `execute`), and to nothing on Codex, whose agent-level `sandbox_mode` is not honoured. This is the leading candidate for 0.2. |
| `model` | Model identifiers are provider-specific. Every harness honours its own native model field, so the field lives in `native`. On Codex it must be paired with `model_reasoning_effort`. |
| `maxTurns` | Claude stops the child partway and lets it resume. OpenCode v2 stops it hard. OpenCode v1 ignores its own field. Codex has none. |
| `skills`, `mcp`, `hooks` | Each embeds a component kind with its own validation and delivery. |

## Versioning

- **Version numbers.** This document has the version `0.1`. Additive changes raise
  the minor version. Before 1.0, any change may be breaking; the change notes will
  say which.
- **How a file's version is known.** It is currently a property of the
  configuration that reads the file, not of the file itself. ADR-0027 records this
  as an open question.

## Informative: native equivalents

These were observed on Claude Code 2.1.283, Codex CLI 0.156.1, OpenCode 1.18.31 and
2.0.17; the evidence is in `.capture/agents`.

| Model field | Claude Code | Codex | OpenCode v1 | OpenCode v2 |
| --- | --- | --- | --- | --- |
| file | `.claude/agents/<name>.md` | `.codex/agents/<name>.toml` | `.opencode/agents/<name>.md` | `.opencode/agents/<name>.md` |
| `name` | frontmatter `name` | `name` | file stem | file stem |
| `description` | frontmatter `description` | `description` | frontmatter `description` | frontmatter `description` |
| `mode` | none: every agent file serves both uses | none: custom agents are subagents | frontmatter `mode` | frontmatter `mode` (absent means `primary`) |
| `instructions` | body | `developer_instructions` | body | body |

A session runs as an agent like this:

| | Claude Code | Codex | OpenCode v1 | OpenCode v2 |
| --- | --- | --- | --- | --- |
| start a session as the agent | `claude --agent <name>`, or the `agent` setting | not possible | `opencode run --agent <name>`, or `default_agent` | the same |
| withhold it from delegation | a permission rule, `Agent(<name>)` in `permissions.deny` | — | `mode: primary` | `mode: primary` |

A package route delivers a definition inside a plugin rather than a project. These
were observed on the same builds:

| | Claude Code | Codex | OpenCode v1 | OpenCode v2 |
| --- | --- | --- | --- | --- |
| route | the plugin's `agents/<name>.md` | none (openai/codex#18988) | a plugin's `config` hook assigns `config.agent[<name>]` | a plugin's `ctx.agent.transform` upserts through `update(<id>, …)` |
| name offered | `<plugin>:<name>`, qualified by Claude | — | the config key | the id |
| a session run as it | `--agent <plugin>:<name>` or the bare name | — | `--agent <config key>`, with `mode: "primary"` | `--agent <id>`, with `mode: "primary"` |
| instructions | body | — | `prompt` | `system` |
| native fields | frontmatter; `permissionMode` is ignored in a plugin agent | — | carried into the config entry | not observed; the plugin API takes OpenCode's internal agent shape |

OpenCode qualifies neither route's names by plugin, so Hooknostic names such an
agent `<plugin>-<name>` itself, as it does for skills.
